# SBOM (Phase 2)

`make sbom VERSION=v1.0 [BOARD=...]` runs Zephyr's own generator, `west spdx`, on the
build and writes SPDX **2.3** tag-value documents to `out/<version>/<board>/sbom/`.
SPDX 2.3 is the newest version `west spdx` supports in Zephyr v4.4.2 (choices: 2.2, 2.3).

## How it is produced

1. `make build` deletes the build directory, runs `west spdx --init` (creates the CMake
   file-based API query) and then `west build`. The init must happen **before** CMake
   configures, otherwise there is no codemodel to read.
2. `app/prj.conf` sets `CONFIG_BUILD_OUTPUT_META=y`. Without `zephyr.meta`, `west spdx`
   stops with "cannot find a valid zephyr.meta".
3. `make sbom` runs `west spdx --analyze-includes --include-sdk` with a namespace that
   contains the version, board and the first 16 hex digits of the `zephyr.elf` SHA-256.

## The five documents

| Document | Contains |
| --- | --- |
| `app.spdx` | the application's source files that are part of a build target |
| `zephyr.spdx` | one package per source tree (Zephyr and each module) with the source files that are part of a build target, plus included headers (`--analyze-includes`) |
| `build.spdx` | the build outputs: one package per CMake target (static libraries) and `zephyr.elf` with SHA-1 and SHA-256, linked by `GENERATED_FROM` relationships to the source files in `app.spdx`, `zephyr.spdx` and `sdk.spdx` |
| `modules-deps.spdx` | one package per module, carrying the CPE/PURL identifiers declared in each module's `zephyr/module.yml` (`security: external-references`) |
| `sdk.spdx` | SDK/toolchain header files included by the build (`--include-sdk`) |

### Which document lists the files compiled into the image?

`build.spdx`. It describes `zephyr_final` (the image), whose prerequisites are the
static libraries; each library is `GENERATED_FROM` the individual source files listed in
`zephyr.spdx`/`app.spdx`. `zephyr.spdx` alone is only the file *inventory* per source tree.

Important for scenario 3: **"compiled" does not mean "contains code".** Mbed TLS's
CMake adds every library source file to the build regardless of Kconfig, and the
feature is removed by `#if` inside the file. So `zephyr.spdx`/`build.spdx` list
`ssl_tls13_client.c` although TLS 1.3 is disabled. In the linker map the object
contributes 0 bytes of `.text`, and the ELF has no TLS 1.3 symbols. Proof of absence
therefore needs the file list **plus** `.config` **plus** the linker map/symbols.

## Identifiers (who has CPE/PURL)

| Component | Identifier source | Status |
| --- | --- | --- |
| zephyr | generated by `west spdx` from the git tag `v4.4.2` | CPE + PURL (only if the tag is present locally, see below) |
| mbedtls | `module.yml` of the Zephyr fork | CPE + PURL for upstream Mbed TLS 4.1.0 |
| tf-psa-crypto | `module.yml` | CPE + PURL for TF-PSA-Crypto 1.1.0 |
| cmsis_6 | none | missing (git SHA only) |
| hal_rpi_pico | none | missing (git SHA only) |
| app | none | missing |
| SDK (one package) | none | missing; no version either |

Findings worth showing:

- **The Zephyr CPE depends on a git tag being present.** `west spdx` derives the Zephyr
  version, CPE and PURL from `git tag --points-at HEAD`. Our `west update --narrow
  --depth=1` fetches no tags, which silently produced a Zephyr package with only a
  commit SHA: no CPE, no PURL, invisible to CPE-based scanners. `make fetch` now
  fetches exactly the pinned tag and `make doctor` checks it points to the pinned commit.
- **The module identifiers describe upstream, the code is a fork.** `mbedtls` is
  `zephyrproject-rtos/mbedtls` at `a3e190fe` with Zephyr patches, but its PURL says
  `pkg:github/Mbed-TLS/mbedtls@v4.1.0`. Scenario 2 builds on this.
- **The C library is not a component.** The board build links `libc.a` (picolibc) and
  `libgcc.a` from the Zephyr SDK; `sdk.spdx` lists only headers in one unversioned
  `sdk` package. native_sim links the host C library dynamically and it does not
  appear at all. `make sbom` reports both gaps; Phase 4 adds them via
  `identifiers/component-map.yaml`.
- **Identifiers sit in a different document than the sources.** `zephyr.spdx` and
  `modules-deps.spdx` describe the same module as two packages with different SPDX IDs.
  Phase 4 merges them into one inventory.

## Not byte-reproducible

Each document has a `Created:` timestamp (current UTC time), and `build.spdx`
references the other documents by SHA-1. Two `make sbom` runs on the same build
therefore differ in those lines only. The firmware is the reproducibility target
(Phase 3); the SBOM is bound to it through the `zephyr.elf` SHA-256 in `build.spdx`
and the namespace.

For native_sim, `build.spdx` hashes `zephyr.elf`; the runnable `zephyr.exe` produced
by the native simulator runner is not described.
